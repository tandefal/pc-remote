# PC Remote — правила разработки

## Перед началом работы

1. Прочитать этот файл и `docs/PROJECT_MAP.md`.
2. Использовать карту проекта для выбора нужных файлов; не сканировать весь репозиторий без причины.
3. Искать точечно через `rg` по именам файлов, типов и методов.
4. Читать только относящиеся к задаче фрагменты больших файлов.

## Архитектура и зависимости

1. Проект состоит из одного Windows-приложения (`windows/`) и одного Android-приложения (`android/`).
2. Не создавать отдельные службы, фоновые EXE, микросервисы или дублирующие компоненты.
3. Не добавлять зависимости и абстракции без практической необходимости.
4. Все пользовательские строки интерфейса должны быть на русском языке.
5. Управление Windows разрешено только после серверной проверки авторизации и целевого объекта.
6. Не логировать токены, pairing-секреты, приватные ключи и содержимое QR-кодов.
7. Не добавлять произвольное выполнение команд и не открывать сервер в интернет.

## Безопасная проверка

1. Не выключать и не блокировать рабочий компьютер во время тестов без явного разрешения пользователя.
2. Не завершать реальные пользовательские приложения; для тестов использовать только безопасно созданные процессы.
3. Не отмечать возможность как «Проверено» без фактического теста.
4. WPF собирать только на Windows с подходящим .NET SDK или совместимым Windows-контейнером; не пытаться собирать WPF в Linux-контейнере.
5. Использовать имеющиеся Android Studio, JDK, Android SDK и Gradle Wrapper; не устанавливать их повторно.

## Документация после каждой задачи

1. Проверить изменения структуры, компонентов, API и связей.
2. При необходимости точечно обновить `docs/PROJECT_MAP.md`.
3. При изменении постоянных правил обновить этот файл.
4. При изменении сборки, установки или использования обновить `README.md`.
5. Не превращать карту проекта в журнал изменений и не оставлять устаревшие пути.

## Стиль работы

1. Не создавать дубли существующего кода.
2. Не добавлять функции за пределами технического задания.
3. Не оставлять обязательную функциональность в виде заглушек.
4. Сохранять архитектуру простой и поддерживаемой.
5. Перед завершением выполнять доступные сборки и тесты.
6. В отчёте кратко указывать: что сделано, что проверено, ограничения и состояние документации.
7. Не запускать полную сборку после каждого незначительного изменения; собирать на значимых контрольных точках.
8. Не создавать дополнительные Markdown-файлы без необходимости.

## Публикация релиза

1. Не публиковать релиз при упавших или незавершённых обязательных проверках CI выпускаемого коммита.
2. Перед публикацией проверить релизные сборки, подпись Android APK и контрольные суммы вложений.
